# Security

Minke's security model is built on minimalism, immutability, and the elimination of trust dependencies. This page covers the protocol's threat model, mitigations, and audit status.

## Threat Model

### In Scope

| Threat | Mitigation |
|---|---|
| Reentrancy attacks | Checks-Effects-Interactions pattern; no external calls before state updates |
| Integer overflow/underflow | Solidity 0.8+ built-in overflow protection |
| Oracle manipulation | No oracles used — DFI schedules are deterministic |
| Admin key compromise | No admin keys on deployed contracts |
| Flash loan attacks | VT pricing is not oracle-dependent; no liquidation mechanism |
| Front-running | `checkpointVesting` is idempotent; front-running has no profit motive |

### Out of Scope (by Design)

| Threat | Why Not in Scope |
|---|---|
| Underlying token risk | Minke is neutral — VT value tracks the underlying token |
| AMM price manipulation | VT/underlying AMM price is not used as an oracle inside Minke |

## Smart Contract Architecture Security Properties

### No Admin Functions

After deployment, there are no privileged functions that any address — including the Minke team — can call to:
- Change fee parameters
- Withdraw user funds
- Modify vesting schedules


### Immutable Vesting Schedules

`vestStart`, `vestEnd`, and total deposited amount are stored as immutable variables. They cannot be changed after tranche creation. This guarantees that VT holders can always predict exactly when and how much they will receive.

### Accumulator Precision

`accVTPerShare` is stored with 1e18 precision. The accumulator pattern is a well-tested design (used in MasterChef and hundreds of derivatives). The key invariant:

```
Σ (userStaked[u] × accVTPerShare / 1e18 - userDebt[u]) 
  ≤ IERC20(underlying).balanceOf(address(this))
```

This inequality holds at all times — the total claimable rewards never exceed the available balance.

### Phase 2 Invariant

The Phase 2 redemption formula maintains:

```
Σ redeemVT(u) = excessT  (exactly)
```

Because `redeemed = vtAmount × (excessT / totalSupplyAtEnd)` and all VTs are burned on redemption, the contract balance reaches exactly 0 after all VTs are redeemed.
