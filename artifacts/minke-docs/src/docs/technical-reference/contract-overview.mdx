# Contract Overview

Minke's smart contract system consists of four primary contracts. Each is minimal, auditable, and purpose-fit.

## Architecture Diagram

```
User/Protocol
    │
    ▼
VestingFactory ──creates──▶ VestingToken (per tranche)
    │                           │
    │                           ├── stakeVT()
    │                           ├── claimT()
    │                           ├── endVesting()
    │                           └── redeemVT()
    │
    └──registers──▶ ContractRegistry
    │
    └──creates──▶ BuybackPool (per tranche)
```

## Contracts

### VestingFactory

**Role:** Entry-point factory. Creates Suites, Tranches, and their associated VestingToken and BuybackPool contracts.

**Key functions:**

| Function | Description |
|---|---|
| `createSuite(token, name)` | Create a new Suite for an underlying ERC-20 |
| `createTranche(suiteId, amount, start, end)` | Create a tranche and deposit underlying |
| `getSuite(suiteId)` | Read Suite metadata |
| `getTranche(trancheId)` | Read Tranche metadata |

### VestingToken

**Role:** The ERC-20 VT contract for a single tranche. Manages staking, pro-rata distribution, and Phase 2 redemption.

**Key functions:**

| Function | Phase | Description |
|---|---|---|
| `stakeVT(amount)` | 1 | Deposit VT to earn unlocks |
| `unstakeVT(amount)` | 1 | Withdraw VT from staking pool |
| `claimT()` | 1 | Claim pending pro-rata unlocks |
| `checkpointVesting()` | 1 | Update accumulator, distribute new unlocks |
| `convertViaBuyback(amount)` | 1 | Exit via BuybackPool |
| `endVesting()` | Transition | Close Phase 1, open Phase 2 |
| `redeemVT(amount)` | 2 | Burn VT, receive pro-rata excessT |

### ContractRegistry

**Role:** On-chain registry mapping Suite/Tranche IDs to deployed contract addresses. Used by frontends, indexers, and integrators to discover active tranches.

**Key functions:**

| Function | Description |
|---|---|
| `registerSuite(suiteId, suiteAddr)` | Called by VestingFactory on Suite creation |
| `registerTranche(trancheId, vtAddr, poolAddr)` | Called on Tranche creation |
| `getSuiteAddress(suiteId)` | Look up Suite contract |
| `getTrancheContracts(trancheId)` | Look up VT and BuybackPool for a tranche |

### BuybackPool

**Role:** Holds 5% of deposited tokens per tranche. Provides Phase 1 exit liquidity for stakers.

**Key functions:**

| Function | Phase | Description |
|---|---|---|
| `convertViaBuyback(vtAmount)` | 1 | Called via VestingToken; pay out pool share |
| `poolBalance()` | Any | Current balance of underlying in pool |

## Contract Relationships

- `VestingFactory` owns `VestingToken` deployment (it calls the constructor)
- `VestingToken` holds underlying assets and mints/burns VTs
- `BuybackPool` is a satellite contract deployed alongside `VestingToken`
- `ContractRegistry` is a standalone registry with no asset custody

## Upgradeability

None of the contracts are upgradeable proxies. Each deployment is immutable. Protocol improvements are deployed as new contract versions; existing tranches continue running on their original code.

<Callout type="warning" title="Immutability guarantees">
The immutability of deployed contracts is a security feature, not a limitation. It guarantees that the rules of your tranche cannot change after creation, regardless of what happens to the Minke team or governance.
</Callout>

## Dependencies

- **OpenZeppelin ERC-20** — VestingToken inherits from OZ's audited ERC-20 implementation
- **No external oracle** — the system has zero Chainlink, Pyth, or other oracle dependencies
- **No governance tokens** — protocol parameters are set at deployment, not via governance votes
