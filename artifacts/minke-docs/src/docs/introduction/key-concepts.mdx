# Key Concepts

A reference glossary for Minke Finance protocol terminology.

## Core Primitives

### Vesting Token (VT)

An ERC-20 token representing a 1:1 claim on the underlying asset from a specific tranche. VTs are fungible within a tranche, tradable on any AMM, and redeemable for the underlying at maturity.

- **Minted**: when a holder deposits a future-income position
- **Burned**: when a holder redeems at maturity (1:1 plus excess)
- **Ratio**: always 1 VT = 1 underlying token (at maturity)

### Yield Token (YT)

An ERC-20 representing rights to the variable yield of a VFI position. YTs are a Phase 2 primitive — they allow yield stripping for speculative or hedging purposes.

### DFI (Deterministic Future Income)

Any on-chain future income where both the total amount and the vesting/unlock schedule are known at origination. Examples: team vesting, SAFTs, node license rewards, tokenized bond coupons.

### VFI (Variable Future Income)

On-chain future income where the amount depends on future market conditions. Examples: lending APY, LP fees, restaking rewards. Addressed by Phase 2 YT.

## Protocol Contracts

### VestingFactory

The entry-point contract. Protocols and institutions call `VestingFactory` to:
1. Create a new **Suite** (collection of tranches for one underlying token)
2. Create a **Tranche** (a specific vesting schedule within a Suite)
3. Deposit underlying tokens and receive VTs

### VestingToken

Each tranche deploys one `VestingToken` — the ERC-20 contract that issues VTs for that tranche. Two phases:
- **Phase 1** — staking and rewards distribution (`stakeVT`, `claimT`)
- **Phase 2** — 1:1 redemption for excess tokens (`redeemVT`)

### ContractRegistry

A registry contract that maps Suite/Tranche identifiers to deployed contract addresses. Used by frontends and integrators to discover active tranches.

### BuybackPool

A liquidity pool seeded by protocol fees. VT holders can convert staked positions to liquid claims through the BuybackPool at any time during Phase 1.

## Mechanics

### Suite

A logical grouping of tranches for a single underlying ERC-20. One protocol = one Suite = many Tranches.

### Tranche

A single vesting schedule within a Suite. Each Tranche has:
- A fixed vesting start and end time
- A total underlying amount
- Its own `VestingToken` contract

### accVTPerShare

A per-share accumulator used by `VestingToken` to track how much underlying has vested per VT held. Inspired by Chef-style staking contracts. Updated on each checkpoint.

```
pendingReward = (userVT × accVTPerShare) - userDebt
```

### Checkpoint

A periodic update to `accVTPerShare` that distributes newly vested tokens proportionally to all active stakers. Anyone can trigger a checkpoint; the protocol is permissionless.

## Lifecycle States

| State | Description |
|---|---|
| **Active (Phase 1)** | Vesting is in progress. VT holders can stake and claim pro-rata unlocks. |
| **Post-vest (Phase 2)** | All tokens have vested. `endVesting()` is called. Excess T has accumulated. Holders can `redeemVT` 1:1. |

### endVesting

The transaction that closes Phase 1 and opens Phase 2. Called after the vesting end time. Triggers the final accumulator update and transfers excess tokens to the `VestingToken` contract for redemption.

---

## Economic Terms

### Present Value (PV)

The market-determined value today of a future cash flow. In Minke, VTs trade at a discount to par (1 underlying) until maturity. The discount reflects time value and risk.

### Excess Tokens

The difference between tokens deposited minus protocol fee (eg. 95%) and tokens actually claimed via staking. Accumulates over Phase 1 and becomes available for 1:1 redemption in Phase 2.

### Protocol Fee

eg.5% of deposited tokens are allocated to the protocol at tranche creation. These seed the BuybackPool and fund protocol operations.

<Callout type="note">
The fee split is fixed at contract deployment. There is no admin key that can change fee parameters post-deploy.
</Callout>
